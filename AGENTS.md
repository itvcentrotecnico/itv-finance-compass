- Finance modules are declared in `src/lib/modules.ts` and rendered by the `/$modulo` route; add new modules to the registry, not new ad-hoc routes. Why: navigation and pages stay in sync as the platform grows.
- Role/permission matrix lives in `src/lib/auth/permissions.ts`; it must be mirrored in backend RLS once auth is enabled — UI checks alone are never authoritative.
- Financial pages live under `src/routes/_authenticated/` (client-only gate that loads the user's active role from `financeiro_hml.perfis`); auth pages stay public. Why: no financial UI renders without a verified session and active profile.
- App data lives in the `financeiro_hml` schema, accessed via `.schema('financeiro_hml')` (not in generated types); privileged auth admin calls (invites) run only in `src/lib/usuarios.functions.ts` after verifying `tem_papel` as the caller. Why: RLS stays the authority and service_role never reaches the browser.
- Financial registries write via the browser client under RLS (`src/lib/cadastros.ts`); audit trail (`financeiro_hml.auditoria`) and authorship are filled only by DB triggers and never written by the app. Why: the database stays the single authority for permissions and history.
- Treasury writes use authenticated TanStack server functions calling role-validated transactional SQL RPCs; immutable operation/effect records and database aggregates are the only balance authority. Why: atomicity, idempotency and exact decimal money must hold even for direct API callers.
- Treasury monetary values cross JavaScript boundaries as decimal strings and use bigint cents only for formatting/validation; never Number arithmetic. Why: large values and cents must remain exact.
- Treasury submissions persist one unresolved request per user/project in browser storage before RPC under an origin-wide Web Lock; recovery queries the caller-owned key before explicitly retrying identical content, and only confirmation or initial explicit rollback clears it. Why: close/reload, competing tabs and lost responses must not create replacement financial operations.
- Treasury operation history uses its own RPC contract and caller-RLS reversal lookup, separately from effect statements. Why: zero-effect openings/reversals and single transfers must remain visible without altering SQL or balance authority.
- Treasury correction and reversal scripts acquire fail-fast exclusive table locks before empty-state checks in the same READ COMMITTED transaction, after draining RPCs in maintenance; local concurrency tests use an isolated database and authenticated roles. Why: prevent preflight write races without silently waiting on old function executions or touching HML.
- Treasury maintenance proposals keep admission SQL separate from the approved migration; a database-level admission gate requires a fixed recovery connection to another database in the same cluster, complete voluntary physical-client drain and background-writer control before the fixed migration connection proceeds. Why: closing admission neither stops existing queries nor proves hosted services are drained, and PostgreSQL rejects closing the current database from itself.
- Spreadsheet-origin records enter `financeiro_hml.tesouraria_conferencias` (keyed by unique `referencia_origem`) and affect balances only via `tesouraria_lancar_conferencia` once conciliated; official accounts start in `contas_preparadas` and become operational only via `tesouraria_habilitar_conta` with validated opening. Why: card settlement, mixed payments and missing account links must never reach balances by assumption.
- Integração GESTÃO ITV → HML é unidirecional e somente leitura na origem: o servidor lê com identidade dedicada (token de servidor GESTAO_ITV_READ_TOKEN no endpoint GET /api/public/integracao-financeiro da origem), registra em `integracao_itens`/`integracao_sincronizacoes` via RPCs com verificação de perfil e cria conferências pendentes apenas de recebimentos efetivos. Why: saldos só mudam pela conciliação humana (M3.3); a origem nunca é alterada e a credencial nunca vai ao navegador.
- Auth email links (recovery/invite) always redirect to the official domain via `urlRetorno` in `src/lib/auth/recuperacao.ts`, and the set-password form only unlocks after the link token itself is validated. Why: old/preview domains broke recovery and a plain session must never allow a password change.
- Automatic daily GESTÃO ITV sync is triggered only by an external scheduler calling POST /api/public/integracao/sincronizacao-diaria with INTEGRACAO_CRON_SECRET (separate from the source read token); the handler runs as service_role solely to call `integracao_iniciar_automatica`/`integracao_concluir`, and the database enforces one running sync, one automatic completion per Manaus day and an attempt cap. Why: no logged-in user is available at schedule time, and the DB stays the authority for concurrency and idempotency.
- Service-role RPC access to financeiro_hml requires explicit schema USAGE in addition to function EXECUTE; validate both using the real database ACL in isolated tests. Why: SECURITY DEFINER does not bypass the caller's schema resolution permissions.
- Manual and automatic source reads share integracao-leitura.server, dynamically imported on the server; log only allowlisted diagnostic fields and reject invalid pagination/JSON. Why: source failures must stay distinguishable without leaking credentials or producing false empty success.
